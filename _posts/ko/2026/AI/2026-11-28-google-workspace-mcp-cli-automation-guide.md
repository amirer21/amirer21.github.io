**Gmail·Drive를 AI 에이전트와 연결하려면, 대화형 앱에서는 공식 원격 MCP 서버를, 터미널 기반 개발 환경에서는 공식 `gwscli`를 먼저 검토하시면 됩니다.** Google이 두 도구의 정식 제공을 발표했습니다. 다만 연결 방식, 계정 권한, 사용량 등급을 따로 확인해야 하며, 정식 발표가 모든 계정의 즉시 사용을 뜻하지는 않습니다.

[발표일은 2026년 11월 24일][release]입니다. 이 글은 **11월 28일 한국 시간에 확인한 공식 문서**를 기준으로 도입 판단을 돕습니다. 직접 계정을 연결하거나 자동화를 실행한 체험기는 아닙니다.

## 핵심 요약

- Google이 운영하는 MCP 서버로 Workspace의 도구를 호출할 수 있습니다.
- 터미널에서 작업하는 에이전트에는 공식 CLI인 **gwscli**가 별도 선택지입니다.
- Standard 등급의 무료 사용 한도와 AI 모델의 구독·호출 비용은 구분해야 합니다.
- 2027년 2월의 에이전트 접근 방식 변경과 4월의 과금 시행을 서로 다른 일정으로 관리해야 합니다.

## 무엇이 정식 제공되었나요?

[Google 발표][release]는 Gmail·Drive·Docs·Sheets·Slides·Calendar·Chat·Tasks의 MCP 서버와 Workspace CLI를 정식 제공한다고 안내합니다. Keep은 향후 제공 대상으로 표시되어 있습니다.

MCP는 AI 앱이 외부 도구와 데이터를 이용하도록 연결하는 규약입니다. 여기서 서버는 Google이 제공하고, Claude나 Antigravity 같은 앱이 클라이언트 역할을 합니다. 문장을 이해하는 모델과 메일·파일을 실제로 다루는 연결 도구가 함께 동작하는 구조입니다.

[개발자 릴리스 노트][notes]는 Gmail·Calendar 등 일부 서버가 계정에 제공되기까지 최대 10일이 걸릴 수 있다고 설명합니다. 전체 발표의 배포 계획은 약 2주입니다. 오늘 메뉴가 보이지 않는다면 배포 진행과 조직 설정을 함께 확인하십시오. 한국의 모든 계정에서 접속이 되는지는 이 글에서 검증하지 않았습니다.

## MCP와 CLI 중 무엇을 고르면 좋을까요?

| 작업 환경 | 먼저 검토할 방식 | 선택할 때 볼 점 |
|---|---|---|
| Claude 같은 대화형 앱에서 메일·파일 활용 | 원격 MCP 서버 | 앱의 커넥터·OAuth·승인 UI 지원 |
| Codex·Claude Code 등 터미널 작업 | 공식 gwscli | 로컬 설치·인증·에이전트의 도구 실행 환경 |
| 기존의 정해진 업무 처리 프로그램 | 현재 API 구조와 새 접근 요건 검토 | AI 에이전트 접근과 일반 앱 호출을 구분 |

위 표는 문서에 근거한 **도입 제안**이며 성능 순위가 아닙니다. 같은 요청이라도 도구 선택, 데이터 범위, 재시도 횟수에 따라 결과와 비용이 달라질 수 있습니다.

[CLI 문서][cli]는 `gwscli`가 Claude Code·Codex·Antigravity와 연결되며, 별도의 커뮤니티 프로젝트인 `gws`와 구분된다고 명시합니다. 검색 결과에서 이름이 비슷한 저장소를 발견하셨다면 설치 대상부터 확인하는 편이 좋습니다.

CLI는 명령과 스키마를 실행 시점에 발견하는 구조입니다. 오래된 명령 예제를 그대로 고정하기보다 현재 도움말과 스키마를 확인하도록 자동화 절차를 설계하십시오. 업데이트 뒤에는 함께 설치한 에이전트용 스킬도 갱신해야 합니다.

## 연결은 어떤 순서로 준비하나요?

[공식 MCP 설정 안내][setup]를 기준으로 준비할 흐름은 다음과 같습니다.

1. 사용할 Google Cloud 프로젝트와 AI 앱을 정합니다.
2. 개인 계정 하나를 연결한다면 Personal mode 설정을, 여러 사용자에게 제공한다면 다중 사용자용 설정을 확인합니다.
3. OAuth 클라이언트의 **Use this client for an AI-powered agent** 설정을 확인합니다.
4. 필요한 Workspace 서비스만 활성화하고 앱에 해당 서버를 연결합니다.
5. 로그인·동의를 마친 뒤, 허용된 데이터가 의도한 범위인지 작은 요청으로 점검합니다.

이 과정에서 발급한 비밀값은 채팅이나 저장소에 붙여넣지 말고 도구의 자격 증명 설정으로 관리하십시오. 조직 계정이라면 관리자의 앱 접근 정책도 적용됩니다.

MCP 기본 엔드포인트인 `/mcp/v1`은 사용자 승인 폼을 지원하는 호스트를 전제로 합니다. 이를 지원하지 않는 호스트용 `/mcp/v1self`는 노출되는 도구와 결과에 제약이 있습니다. 주소를 바꾸면 같은 기능이 모두 유지된다고 가정하지 마십시오.

CLI를 선택했다면 [설치·인증 안내][cli]에서 운영체제에 맞는 배포본을 고른 뒤 본인 터미널에서 로그인하십시오. 원격 SSH나 컨테이너에서는 브라우저의 로컬 콜백이 돌아오지 않아 대화형 인증이 끝나지 않을 수 있습니다.

## 무료 한도와 비용은 어떻게 읽어야 하나요?

[사용량 등급 문서][quota]는 Standard 등급의 GA MCP 서버에 **프로젝트별·제품별 하루 최대 5,000요청** 한도와 별도의 분당 제한을 안내합니다. 무료 등급은 Google Cloud 결제 계정 없이 시작할 수 있습니다.

주의할 점은 **MCP 도구 한 번 호출이 항상 요청 한 번으로 계산되는 것은 아니라는 것**입니다. 내부에서 여러 API 호출을 하는 도구가 있으므로, 대화 횟수를 그대로 사용량으로 계산하면 오차가 납니다.

| 구분 | 확인할 내용 |
|---|---|
| Standard | 무료이며 공개된 사용 한도를 적용 |
| Scaled | 결제 계정 연결 필요. 선택만으로 할당량이 자동 증가하지 않음 |
| 2027년 4월 1일 이후 Scaled의 Gmail·Calendar·Drive MCP | 일일 무료분 없이 첫 성공 요청부터 과금한다고 세부 문서가 명시 |

발표 블로그는 무료분 초과 과금을 포괄적으로 설명하지만, **세부 문서는 Scaled의 REST API와 MCP의 무료분을 다르게 구분**합니다. 도입 비용은 세부 문서와 프로젝트의 비용 추정 화면을 기준으로 다시 확인하십시오.

이 글은 토큰당 API 가격이나 월 예상 금액을 계산하지 않습니다. 위 한도는 Workspace 데이터 접근에 관한 내용이며, 이를 호출하는 AI 서비스의 구독·모델 이용료까지 무료라는 의미는 아닙니다.

## 기존 REST 자동화는 언제 검토해야 하나요?

[공식 안내][release]는 AI 에이전트나 유사 접근 도구가 Workspace 데이터를 이용할 때 MCP 서버 또는 Workspace CLI를 사용해야 하며, **기술적 적용이 2027년 2월 1일 시작**된다고 설명합니다. 일반 앱의 모든 REST API가 사라진다는 발표로 해석해서는 안 됩니다.

개발 중인 도구가 있다면 다음처럼 정리해 보십시오.

| 확인할 항목 | 기록할 내용 |
|---|---|
| 호출 주체 | 일반 프로그램인지, AI 에이전트인지 |
| 접근 대상 | Gmail·Drive·Calendar 중 실제 필요한 제품 |
| 동작 | 검색·읽기·초안 작성·전송·공유 중 필요한 작업 |
| 규모 | 하루 사용량과 반복 호출·재시도 횟수 |
| 일정 | 2월 접근 방식 적용, 4월 과금 적용을 각각 관리 |

기존 서비스를 한 번에 바꾸기보다, 호출 지점을 분류하고 새 연결로 같은 결과가 나오는지 비교할 수 있는 작업부터 옮기는 방식을 권합니다. 정확한 적용 범위는 해당 프로젝트의 최신 안내를 다시 확인하셔야 합니다.

## 첫 자동화는 무엇으로 시작하면 좋을까요?

다음은 제품 성능을 시험한 결과가 아닌 **업무 설계 예시**입니다.

> 특정 프로젝트의 최근 메일과 관련 문서를 찾아, 진행 상황·미결정 사항·근거 링크를 표로 정리해 주세요. 결과에 사용한 메일과 문서를 표시해 주세요.

첫 목표를 ‘자동 전송’보다 ‘근거가 남는 요약’으로 잡으면 검증하기 쉽습니다. 같은 업무를 수동으로 정리한 결과와 비교하면서 다음을 살펴보십시오.

- 지정한 기간·프로젝트 밖의 자료가 섞였는지 확인합니다.
- 사실과 모델의 추정을 구분했는지 확인합니다.
- 링크를 열어 요약의 근거를 추적할 수 있는지 확인합니다.
- 작업 실패 시 같은 호출을 끝없이 반복하지 않는지 확인합니다.

그다음 초안 작성과 실제 전송을 나누어 확장하시면 됩니다. 읽기 품질과 변경 동작을 따로 평가해야 어느 단계에서 오류가 생겼는지 찾기 쉽습니다.
