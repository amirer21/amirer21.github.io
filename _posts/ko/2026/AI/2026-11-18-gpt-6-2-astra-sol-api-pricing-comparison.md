**GPT-6.2 Astra는 어려운 추론·코딩 작업을, GPT-6.2 Sol은 일상적인 코딩과 에이전트 작업을 겨냥합니다.** 두 모델을 비교할 때 먼저 볼 부분은 가격 차이와 현재 연동 방식입니다. 특히 외부 함수를 호출하는 프로그램이라면 모델명 교체 전에 API 종류부터 확인해야 합니다.

OpenAI의 [공식 API 변경 기록][changelog]은 2026년 11월 17일 항목에서 두 모델을 안내합니다. 이 글은 **2026년 11월 18일 한국 시간에 확인한 공식 OpenAI 문서**를 바탕으로 정리했습니다. 직접 사용한 성능 후기나 독립 벤치마크 결과는 포함하지 않았습니다.

## GPT-6.2 Astra와 Sol, 무엇이 다른가요?

[공식 사용 가이드][guide]는 가장 까다로운 작업에는 Astra를, 더 낮은 비용으로 복잡한 작업을 처리하려면 Sol을 제시합니다.

| 항목 | GPT-6.2 Astra | GPT-6.2 Sol |
|---|---|---|
| API 모델 ID | `gpt-6.2-astra` | `gpt-6.2-sol` |
| 공식 용도 안내 | 어려운 추론과 코딩 | 일상적인 코딩과 에이전트 작업 |
| 입력·출력 | 텍스트·이미지 입력, 텍스트 출력 | 텍스트·이미지 입력, 텍스트 출력 |
| 컨텍스트 창 | 1,050,000 토큰 | 1,050,000 토큰 |
| 최대 입력 / 출력 | 922,000 / 128,000 토큰 | 922,000 / 128,000 토큰 |

사양은 [Astra 모델 문서][astra]와 [Sol 모델 문서][sol] 기준입니다. 컨텍스트 창과 최대 입력 길이는 같은 숫자가 아니므로, “100만 토큰 모델이니 입력도 100만 토큰을 넣을 수 있다”고 해석하면 안 됩니다.

위 표의 용도는 공급자가 제시한 방향입니다. 내 코드베이스나 한국어 문서에서도 어느 모델이 더 나은지는 별도로 평가해야 합니다.

## API 가격: Astra는 Sol의 4배입니다

다음은 **Standard 처리 방식·짧은 컨텍스트 기준**, 텍스트 100만 토큰당 미국 달러 가격입니다. 확인일은 2026년 11월 18일입니다.

| 모델 | 일반 입력 | 캐시된 입력 | 출력 |
|---|---:|---:|---:|
| GPT-6.2 Astra | US$8.00 | US$0.40 | US$40.00 |
| GPT-6.2 Sol | US$2.00 | US$0.10 | US$10.00 |

출처: [공식 API 가격표][pricing].

같은 종류와 수량의 토큰을 같은 처리 방식으로 쓴다면 Astra의 표기 단가는 Sol의 4배입니다. 다만 **작업 한 건을 끝내는 비용까지 항상 4배라는 뜻은 아닙니다.** 모델마다 사용 토큰과 재시도 횟수가 달라질 수 있기 때문입니다.

현재 가격표에서 이전 GPT-6 Astra의 일반 입력·출력 단가는 US$10·US$50입니다. GPT-6.2 Astra의 US$8·US$40은 이 기준에서 각각 20% 낮습니다. 이는 단가 비교이며 실제 업무 비용 절감률을 측정한 결과는 아닙니다.

### 입력 1만·출력 2천 토큰이면 얼마인가요?

캐시와 별도 도구 비용이 없고, **과금 대상 출력 토큰**이 2천 개라고 가정한 계산입니다.

| 모델 | 입력 비용 | 출력 비용 | 합계 |
|---|---:|---:|---:|
| Astra | 10,000 ÷ 1,000,000 × 8 = US$0.08 | 2,000 ÷ 1,000,000 × 40 = US$0.08 | **US$0.16** |
| Sol | 10,000 ÷ 1,000,000 × 2 = US$0.02 | 2,000 ÷ 1,000,000 × 10 = US$0.02 | **US$0.04** |

이 표는 요금 구조를 이해하기 위한 예시입니다. 실제 청구액은 요청별 사용량과 적용 요율로 확인해야 합니다. 화면에 표시된 답변 글자 수를 그대로 토큰 수로 계산하지 마세요.

### 긴 입력과 빠른 처리 옵션은 별도입니다

모델 문서는 **입력이 272K 토큰을 초과하는 요청**에 대해 전체 요청의 입력·캐시 요율은 2배, 출력 요율은 짧은 컨텍스트의 1.5배가 적용된다고 안내합니다. 위 표를 긴 코드베이스 분석 비용에 그대로 적용하면 예상이 틀릴 수 있습니다.

캐시된 입력을 읽는 가격과 캐시를 쓰는 가격도 다릅니다. Batch·Flex·Fast·Ultrafast 등 처리 방식까지 포함한 견적은 [최신 가격표][pricing]에서 조건을 맞춰 확인해야 합니다. 이 글의 금액은 ChatGPT 구독료가 아닌 **API 단가**입니다.

## 도구 호출에는 Responses API가 필요합니다

[11월 17일 공식 변경 기록][changelog]에서 중요한 안내는 두 가지입니다.

- 두 모델 모두 Responses API와 Chat Completions를 지원합니다.
- **도구 호출은 Responses API가 필요합니다.**

일반 텍스트 답변을 받는 것과, 모델이 외부 함수를 선택해 실행을 요청하는 것은 연동 요구가 다릅니다.

예를 들어 “테스트 로그를 읽고 요약해 달라”는 요청과 “실패한 테스트를 찾아 재실행하고 결과를 저장해 달라”는 요청은 다르게 설계해야 합니다. 두 번째 작업에는 도구를 실행하고 결과를 돌려주는 프로그램 흐름이 필요합니다.

기존 Chat Completions 기반 자동화에 함수를 연결해 사용하고 있다면, 모델 ID만 바꾸기 전에 호출 경로와 응답 처리 방식을 점검하세요.

## 기존 프로그램에서 확인할 변경점

공식 문서는 두 모델에서 추론 강도 `none`을 지정하면 API가 요청을 거부한다고 안내합니다. 기존 설정에 이 값이 남아 있는지 확인해야 합니다. [Astra][astra] · [Sol][sol]

또한 [GPT-6.2 사용 가이드][guide]는 대화 도중 과거 기록을 바꾸거나 모델을 하향 변경하는 등의 상황에서 추론 항목이 제거될 수 있다고 설명합니다. 그 결과 이전 작업을 반복하며 토큰을 더 쓰거나 답변 품질이 떨어질 수 있습니다.

이를 바탕으로 기존 연동에서는 다음을 확인하는 것이 좋습니다.

| 점검 대상 | 확인할 질문 |
|---|---|
| 모델 설정 | 모델 ID와 추론 강도 값이 지원되는가? |
| 도구 실행 | Responses API를 사용하고 결과를 올바르게 전달하는가? |
| 대화 기록 | 매 요청마다 과거 지시나 도구 결과를 수정하고 있지 않은가? |
| 비용 추적 | 긴 입력, 캐시 쓰기, 도구 사용 비용을 구분하는가? |

표는 공식 변경 사항에 근거한 점검 제안입니다. 모든 프로그램에서 같은 문제가 발생한다는 의미는 아닙니다.

## 어떤 모델부터 평가하면 좋을까요?

반복되는 요약·분류·보통 난이도의 코드 수정이라면, **Sol부터 시험하고 부족한 과제에 Astra를 비교하는 방식**을 제안합니다. 공식 단가 차이를 고려한 평가 전략이며, 직접 측정한 우열은 아닙니다.

반대로 여러 서비스에 걸친 오류 분석처럼 한 번의 실수가 큰 수정 비용을 만드는 작업에서는 Astra도 처음부터 비교 후보에 넣을 수 있습니다.

평가할 때는 동일한 요청 몇 개를 준비하고 다음 항목을 기록해 보세요.

1. 요구한 결과를 실제로 완성했는가?
2. 근거 없는 설명이나 누락이 있었는가?
3. 테스트와 실행 확인을 통과했는가?
4. 실패·재시도를 포함한 API 비용은 얼마인가?
5. 사람이 확인하고 고치는 데 몇 분이 걸렸는가?

가령 Sol 결과는 두 번 수정해야 하고 Astra 결과는 바로 사용할 수 있었다면, 토큰 단가만으로 선택하기 어렵습니다. 반대로 둘 다 같은 수준으로 끝낸다면 더 낮은 비용의 선택이 합리적일 수 있습니다.

## 국내 사용자는 무엇을 확인해야 하나요?

이 글에서는 한국 계정으로 두 모델을 호출하거나 계정별 접근 권한을 검증하지 않았습니다. 공식 API 목록에 있다는 사실과 **내 계정에서 지금 사용할 수 있다는 사실**은 구분해야 합니다.

실제 도입 전에는 플랫폼에서 모델 접근 권한·사용 한도·결제 조건을 확인하고 작은 요청부터 시험하세요. ChatGPT나 Codex에서 보이는 모델 선택지 역시 API 이용 조건과 동일하다고 가정하지 않는 편이 좋습니다.

새 모델의 이름보다 먼저 정해야 할 것은 평가 과제입니다. 현재 프로그램에서 자주 실패하는 요청을 골라 같은 기준으로 비교하면, 교체할 이유와 유지할 이유를 구체적으로 판단할 수 있습니다.
