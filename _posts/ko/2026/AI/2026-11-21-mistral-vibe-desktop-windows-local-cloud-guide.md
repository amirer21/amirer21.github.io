**Mistral Vibe Desktop은 문서 작업과 AI 코딩, 로컬 저장소와 클라우드 세션을 한 앱에서 다루는 도구입니다.** Windows에서도 사용할 수 있으며, 로컬 코딩을 시작하기 위해 Vibe CLI를 별도로 설치할 필요는 없습니다.

Mistral의 [공식 릴리스 노트][release]는 **2026년 11월 17일** Vibe Desktop의 정식 제공을 안내했습니다. 오늘 새로 나온 모델 발표가 아닌, 최근 공개된 개발 도구 소식입니다. 이 글은 **2026년 11월 21일 한국 시간에 확인한 공식 문서**를 기준으로 시작 방법과 선택 기준을 정리합니다.

## 무엇이 새로워졌나요?

[릴리스 노트][release]에 따르면 macOS·Windows 앱 안에서 Work와 Code를 이용하고, 파일·명령 실행·Git 변경 사항을 작업 옆에서 확인할 수 있습니다. Linux 지원은 추후 제공 예정으로 안내됩니다.

핵심은 새로운 모델 이름보다 **작업을 요청하고 결과를 확인하는 환경**입니다. 코드를 수정한 뒤 터미널 출력과 변경 내용을 같은 앱에서 살펴볼 수 있다는 점에 초점이 있습니다.

AI가 “완료했습니다”라고 답하더라도 확인할 것은 남습니다. 어떤 파일을 바꿨는지, 실제 실행한 명령은 무엇인지, 테스트 출력이 결과를 뒷받침하는지 보아야 합니다.

## Work와 Code, 어디서 시작해야 하나요?

| 하고 싶은 일 | 먼저 살펴볼 모드 |
|---|---|
| 보고서·문서 비교, 자료 정리 | Work |
| 저장소 구조 분석, 오류 수정 | Code |
| 테스트 실행과 코드 변경 검토 | Code |
| 로컬 자료 폴더를 작업 문맥으로 추가 | Work |

공식 [Work 문서][work]와 [Code 개요][desktop]를 바탕으로 구분한 표입니다.

Work에서는 입력창의 **+ → Folders → Add a folder** 경로로 로컬 폴더를 추가할 수 있습니다. 다만 폴더를 추가했다는 사실과 모든 파일을 이미 읽었다는 사실은 다릅니다. 작업 요청에 대상 자료와 원하는 결과를 명시하는 것이 좋습니다.

예를 들어 “이 폴더를 분석해 주세요”보다 “두 보고서의 변경 내용을 항목별로 비교하고 근거 파일명을 적어 주세요”가 결과를 검토하기 쉽습니다.

## Desktop을 쓰려면 CLI도 설치해야 하나요?

[공식 데스크톱 문서][desktop]는 **별도 Vibe CLI 설치가 필요하지 않다**고 설명합니다. Desktop의 로컬 세션은 CLI와 핵심 에이전트 엔진·세션 로그를 공유하지만, CLI 앱 자체를 포함해 실행하는 방식은 아닙니다.

또한 도구 구현과 프롬프트는 인터페이스에 따라 다를 수 있습니다. 따라서 같은 엔진을 사용한다고 CLI의 모든 기능이나 설정이 Desktop에서도 동일하다고 가정하면 안 됩니다.

여기서 설치가 필요 없다는 것은 **Vibe CLI**에 대한 설명입니다. 프로젝트 실행에 필요한 Python 가상환경, Node 패키지, 데이터베이스까지 자동으로 준비된다는 의미는 아닙니다.

## 로컬 세션과 클라우드 세션 선택 기준

[인터페이스 비교 문서][surfaces]는 Desktop에서 로컬 체크아웃 또는 GitHub 기반 클라우드 세션을 사용할 수 있다고 안내합니다.

| 구분 | 로컬 세션 | 클라우드 세션 |
|---|---|---|
| 작업 위치 | 내 PC의 저장소와 개발 환경 | 관리형 원격 샌드박스 |
| 먼저 고려할 상황 | 이미 복제한 프로젝트, 로컬 의존성 필요 | GitHub 저장소의 독립된 수정 작업 |
| 점검할 사항 | 사용 중인 폴더·런타임·현재 변경 내용 | 저장소 접근 권한·설치 가능한 환경 |
| 결과 확인 | 파일 변경과 명령 출력 | 원격 실행 결과와 브랜치·PR |

로컬에서만 접속되는 서비스가 필요한 테스트라면 로컬 세션이 평가하기 쉬울 수 있습니다. 반대로 공개 저장소의 문서 수정처럼 독립적인 작업은 클라우드가 후보가 됩니다. 이는 환경 선택을 위한 제안이며, 실제 작업 가능 여부는 프로젝트 조건에 따라 확인해야 합니다.

[클라우드 시작 문서][cloud]는 GitHub 저장소를 연결하고 새 세션을 만든 뒤, 생성된 브랜치나 PR을 검토하는 흐름을 안내합니다. **내 PC에 설치된 환경이 클라우드에도 그대로 존재하는 것은 아닙니다.**

## Windows에서 첫 코딩 작업을 시작하는 순서

[공식 첫 작업 가이드][first]를 기준으로 한 기본 흐름입니다.

1. 공식 [릴리스 노트의 다운로드 안내][release]에서 Windows용 앱을 확인합니다.
2. 앱을 설치하고 Mistral 계정으로 로그인합니다.
3. Code로 전환해 작업할 로컬 저장소의 세션을 엽니다.
4. 재현 가능한 오류나 실패한 테스트 하나를 지정합니다.
5. 에이전트의 조사·수정·명령 출력을 확인합니다.
6. 변경 사항을 검토한 뒤 커밋 여부를 결정합니다.

이번 글에서는 Windows 설치 파일의 실제 설치·실행을 시험하지 않았습니다. 다운로드 시 운영체제에 맞는 파일인지 확인하세요. 계정별 접근 권한·사용 한도·요금도 직접 검증하지 않았으므로 로그인 후 표시되는 조건을 확인해야 합니다.

**정식 제공이라는 안내와 무료·무제한 이용은 같은 뜻이 아닙니다.** 요금을 확인하지 않은 상태에서 특정 구독 가격이나 무료 사용량을 전제로 작업을 계획하지 않는 편이 좋습니다.

## 첫 요청은 ‘작은 수정 + 검증 기준’으로

처음부터 프로젝트 전체를 개선해 달라고 요청하면 어떤 변경이 필요했고 무엇이 부작용인지 판단하기 어렵습니다. 기능 하나나 실패 테스트 하나처럼 결과를 확인할 수 있는 범위를 권합니다.

다음은 직접 실행한 기록이 아닌 **요청 예시**입니다.

> 이 저장소에서 아래 오류가 발생하는 경로를 찾아주세요. 먼저 재현 방법과 관련 파일을 확인하고, 기존 함수의 공개 인터페이스를 유지하면서 원인을 수정해주세요. 관련 없는 리팩터링은 제외해주세요. 수정 후 관련 테스트를 실행하고, 실패하거나 실행하지 못한 항목도 그대로 보고해주세요. 변경은 커밋하지 말고 제가 검토할 수 있도록 남겨주세요.
>
> 오류 로그: 실제 로그를 여기에 붙여넣습니다.  
> 재현 순서: 실제 실행 순서를 적습니다.  
> 기대 결과: 정상 동작을 구체적으로 적습니다.

이 요청의 목적은 AI의 설명을 길게 받는 것이 아닙니다. **문제·수정 범위·검증 방법을 연결해 결과를 판단할 수 있게 하는 것**입니다.

## 결과는 어떤 순서로 검수하나요?

공식 가이드는 변경 내용과 테스트 결과를 확인하도록 안내합니다. [첫 작업 가이드][first]

| 검수 단계 | 확인할 질문 |
|---|---|
| 재현 | 처음 제시한 오류를 실제로 확인했나요? |
| 변경 | 원인과 관련된 파일만 수정했나요? |
| 동작 | 기존 요구사항이나 인터페이스를 바꾸지 않았나요? |
| 검증 | 실행한 테스트 명령과 결과가 있나요? |
| 미완료 | 환경 문제로 못 한 검사를 성공처럼 설명하지 않았나요? |

테스트 하나가 통과했다는 사실과 프로그램 전체가 정상이라는 결론도 구분해야 합니다. 변경으로 영향을 받는 경로가 더 있다면 그 범위를 추가로 확인해야 합니다.

독립된 작업을 병행할 때는 별도 작업 디렉터리를 사용하는 Git worktree도 후보입니다. 같은 체크아웃을 여러 세션이 동시에 수정하면 변경의 출처를 추적하기 어려워질 수 있습니다.

## Desktop과 CLI는 어떤 기준으로 고르면 좋을까요?

[공식 비교 문서][surfaces]는 Desktop을 로컬·클라우드 작업을 한 앱에서 다루는 용도로, CLI를 터미널 중심 개발과 스크립팅·CI에 맞는 인터페이스로 구분합니다.

- **파일·명령 결과·변경 내용을 화면으로 확인:** Desktop을 먼저 평가합니다.
- **기존 VS Code 편집 흐름 유지:** VS Code 확장을 비교합니다.
- **명령 기반 반복 작업과 비대화형 실행:** CLI 지원 범위를 확인합니다.
- **로컬 설정 없이 GitHub 저장소 작업:** 웹·클라우드 세션을 검토합니다.

새 도구를 설치했는지보다 **같은 문제를 더 적은 수정과 검토 시간으로 끝냈는지**가 도입 판단에 도움이 됩니다. 기존 도구와 동일한 작은 과제를 비교하고, 결과 품질과 사람이 고친 시간을 함께 기록해 보세요.
